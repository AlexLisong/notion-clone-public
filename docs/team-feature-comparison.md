# Folio small-team feature comparison

The table describes the current personal and native team runtimes. [Behavior references](notion-behavior.md) link to public sources; [architecture](architecture.md) explains the independent implementation. The acceptance matrix below identifies important regression scenarios, not a certification of full product parity.

The intended product is a small team's shared document and task workspace. Accounts are created directly by an administrator with a username, temporary password, and role. **There are no invitations, invitation links, invitation emails, guest onboarding, or public registration.** Granting an existing account access to a page is a permission change, not an invitation flow.

Public Notion help pages were read without logging in or accessing private source, workspace data, or internal APIs. Sources establish documented product behavior; they do not establish Notion's storage, authentication, or synchronization implementation. Folio's SQLite/session design is its own. Notion help text can change, and plan-dependent features are not promises about every Notion account.

## Permission and collaboration contract

- An account's role and a page's effective access are separate. Viewer accounts cannot mutate content, comments, history, attachments, or sharing, even if an edit grant is submitted or inherited. Member edit permission does not confer permission to reshare or change ownership.
- The inherited model takes the union of ancestor team/direct grants. A child under a shared ancestor is therefore not private merely because its own direct setting is private. Ancestor owners can manage their subtree. Team visibility gives members edit access and viewer accounts read access; a narrower direct grant does not subtract inherited access. The UI must show inherited/effective access and workspace administrators' access accurately.
- Checks apply to the complete command and all affected pages. Reparenting, duplicating, trashing, restoring, and sharing a subtree must not move or expose descendants the caller cannot manage.
- Server filtering covers page bodies and metadata, breadcrumbs, searches, relation choices, exports, comment threads, history, activity, notification snippets, and file downloads. Hiding a sidebar item is insufficient.
- Polling is eventual refresh. Remote saved changes can appear after the next successful poll; local unsaved edits remain intact. A same-page conflict requires recovery/reload, not silent last-write-wins. Loss of access stops further reads/writes and clears active restricted views; access revocation cannot retract content already downloaded by a person.
- Comment creation has no idempotency key. Mention IDs are deduplicated within one request, but distinct mention/reply/page-owner event types can notify the same recipient. Retrying a post after an uncertain transport failure can create another comment and another set of inbox events.

## Acceptance matrix

Use disposable accounts, databases and attachments when verifying these scenarios. The [verification guide](verification.md) maps the automated commands to the two runtime paths. Deployment, backup and migration checks must be repeated for the installation being changed.

| ID | Scenario | Required outcome and evidence |
| --- | --- | --- |
| T01 | Anonymous request, expired session, logout, or deactivated account | Protected reads/writes and file bytes are denied. Logout invalidates the server session. Deactivation and password reset/change invalidate existing sessions. Test direct API requests as well as browser navigation. |
| T02 | Admin creates member/viewer; temporary password is used | No email, invitation record/link, or registration route is required. The account must change its temporary password before accessing workspace data. Non-admin attempts to create users/change roles/reset others fail. Prevent removal of the last owner. |
| T03 | Existing personal database is upgraded, then initialization is repeated | Existing pages retain IDs, content, structure, property values, and Trash state; migrated ownership/access starts private to the original owner. Migration is transactional and repeatable. A new member cannot see those private pages. Legacy snapshot GET/PUT is denied after initialization. |
| T04 | Member A owns a private page; member B searches and guesses identifiers | B cannot obtain its title, body, children, counts/snippets, history, activity, comments, linked-record labels, export data, or attachments. Include forged direct API IDs, not only the UI. |
| T05 | Owner grants view/edit, removes it, or changes an ancestor grant | Effective access matches the displayed inherited policy. Existing open tabs stop reading/writing after revocation. A stale sharing dialog cannot re-grant access revoked elsewhere: its access revision must conflict. A viewer cannot bypass the account role ceiling with an edit grant. Mentioning or assigning someone does not silently grant access. |
| T06 | A parent has mixed-access descendants; caller moves/trashes/restores/shares it | The complete subtree operation is authorized and atomic, or it fails without partial changes. Cycles are rejected. Reparenting cannot expand access silently or retain misleading private labels. |
| T07 | Two authenticated users edit different pages from the same initial state | Both saved edits survive refresh and process restart. A stale whole-workspace payload cannot replace unrelated or invisible pages. Verify with two browser contexts and storage/API assertions. |
| T08 | Two users edit the same page; polling/save responses arrive out of order | One stale content revision receives HTTP 409; local unsaved text remains exportable/recoverable. Polling never replaces a dirty editor. Switching account/page during an in-flight response cannot apply another account/page's state. |
| T09 | Member comments, replies, and explicitly mentions another member | Author identity comes from the session; thread and page IDs are checked together. One post creates its comment and applicable inbox events for authorized recipients. An inaccessible recipient gets neither private content nor a notification. Mention IDs are deduplicated within the request; a retry after an uncertain transport result may duplicate the post/events because idempotent delivery is not implemented. |
| T10 | A notification exists before permission is revoked | Inbox fetch/open/reply rechecks current access and hides restricted excerpts. Mark-read/archive operations cannot affect another account's inbox. No external message is sent. |
| T11 | User views history and restores an older page version | History access is authorized; a stale restore conflicts; successful restore creates a new version with the current actor. Old ownership, grants, or unauthorized relation/file references are not resurrected. Ordinary save/history failures preserve the draft. |
| T12 | User uploads, downloads, or removes a file | Enforce page edit/read permissions, streaming size/quota limits, safe filenames, and opaque file IDs. Arbitrary HTML/SVG is downloaded rather than executed on the app origin. Denied/oversized uploads leave no accessible orphan; revoked access blocks old download URLs. |
| T13 | Task has assignee/due date; user switches table/board/calendar/list | Values refer to the same saved record. Calendar respects date-only values in Vancouver and a timezone ahead of UTC; today/month navigation and due filters work. Read-only browsing and view changes do not accidentally save page content. Inaccessible related records remain private. |
| T14 | Admin and ordinary member export or import | Member export excludes inaccessible pages and metadata. Import cannot forge owner IDs, roles, grants, revision/history authors, or attach another page's files. If team import is not supported, it is explicitly unavailable rather than using the personal snapshot endpoint. |
| T15 | Service restarts, a real backup is restored, or code rollback is attempted | Team accounts/pages/ACLs/comments/history and attachment bytes survive; a restored DB has all referenced files. Restored sessions are invalidated. Post-cutover rollback cannot run an old proxy-only-authenticated API behind nginx with Basic auth removed. Verify rollback procedure in disposable storage. |

## Security review and operating boundaries

The native SQLite and session implementation relies on the following operating boundaries. These are design requirements and review guidance, not a claim of exhaustive security coverage.

1. **Guard the cutover and rollback boundary.** The old API trusts the authenticated reverse proxy and returns the full retained personal snapshot. Removing nginx Basic auth and then rolling back to the old binary would remove that authentication boundary. Allow only team-aware code rollback after cutover, or restore the old proxy authentication before starting old code. Persist the team-initialized marker; an unset environment flag must not reactivate the legacy route. Bootstrap failures must fail closed.
2. **Authorize within the write transaction.** Parse and bound input before the transaction; do expensive password hashing outside it. Then re-read active session/account state, effective ACLs, affected descendants, and revisions inside `BEGIN IMMEDIATE` before any mutation. Sharing changes need their own revision check too: stale grant lists must not restore revoked access. Use parameterized statements and a single commit for the command plus history/activity/notification records. Client ownership, authorship, permission, and timestamp fields are never authoritative.
3. **Make sessions revocable and scoped.** Use randomly generated opaque tokens, store token hashes, and set a host-only `Secure`, `HttpOnly`, `SameSite` cookie in production. Recheck account status and role on every request. Temporary-password sessions may only change that password or log out. Clear/invalidate sessions on reset, deactivation, and password change; do not trust role data captured only at login.
4. **Keep the existing origin boundary.** Apply trusted proxy and canonical host/protocol/origin validation to login, logout, password/account changes, page commands, and multipart uploads. Do not relax exact-origin writes just because cookies are SameSite. Use `no-store` on authenticated responses, and clear account-scoped browser state on logout/switch.
5. **Bound authentication and content work.** Use salted asynchronous scrypt with explicit parameters, normalized unique usernames, generic login failures, bounded password/body sizes, and account plus trusted-client-address throttling. Async scrypt still consumes CPU/memory and needs bounded concurrency. Keep SQLite transactions short and requests/pages/comments/history/files within documented limits.
6. **Treat secondary reads as protected content.** Files, historical versions, notifications, exports, and relation titles can bypass an otherwise correct page API. Check current access when reading them. Restore content into a new revision without restoring old ACL/ownership. File bytes must be outside public assets, reached only through authorized opaque IDs, with attachment disposition and `nosniff` for active formats.
7. **Design backups for database/file consistency.** An online SQLite backup alone no longer covers the product. Preserve every file referenced by the captured database, retain files needed by history, and clean orphans safely. Restore checks must include hashes/bytes and invalidate restored sessions, not merely run `PRAGMA integrity_check`. Backups contain password hashes and private content and retain their restricted handling.

## Recommended next items

1. Keep permission, migration, concurrency and actual restore checks in the release process as more collaboration features are added.
2. Add comment-only page access if the team needs reviewers who should not edit documents. Inline/property comments and reactions can follow when page-level discussions become too coarse; page-thread resolve/reopen is already implemented [N2][N4].
3. Add due reminders and per-page notification preferences if task handoffs need more control. Assignment notifications already exist. Define timezone and delivery semantics before adding email/push channels, and add idempotent comment creation if reliable retry behavior becomes necessary [N5][N8].
4. Add safe media previews/alt text and richer relation behavior only for concrete team use cases. Keep previews behind file ACLs and avoid implying that simple links already provide rollups [N7][N10].
5. Consider simultaneous same-page coediting only if conflicts are frequent enough to justify a separate synchronization design. Polling plus revision checks should continue to be described accurately [N3].
